## 一、项目概述

### 1.1 项目背景

随着中国居民膳食多样性提升和营养失衡问题加剧，「吃什么、吃多少、怎么搭配」已成为普通大众的日常困扰。现有营养管理产品普遍存在两个不足：一是记录门槛高（手动输入每顿饭菜重量难以坚持），二是 AI 能力薄弱（仅做通用问答，不结合用户身体数据和当日饮食）。

### 1.2 项目定位

「膳知・AI 营养分析师」是一款面向普通用户的**个性化 AI 营养健康管理工具**。通过 AI 视觉识别降低记录门槛，通过可解释的营养算法给出客观评价，通过 RAG + Agent 增强的大模型对话提供贴身建议，让用户用最自然的方式管理一日三餐。

### 1.3 项目目标

- **降低记录成本**：拍照即知营养，无需手动查食物成分
- **提供可解释评价**：每项超标/偏低都给出人话建议，不堆砌数字
- **打造个性化咨询**：AI 对话助手能「看到」用户身体数据和饮食记录，回答贴合个人情况
- **形成多模态闭环**：图像识别结果可作为结构化上下文继续咨询，并支持中文语音输入与回答播报
- **保证稳定可用**：云端大模型 + 本地知识库 + 规则引擎三层降级，任何网络环境下功能不中断

### 1.4 术语说明

| 术语 | 说明 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Agent | AI Agent，具备工具调用能力的智能体 |
| SSE | Server-Sent Events，服务端推送事件，用于流式输出 |
| GLM-4V | 智谱 AI 的多模态（视觉 + 文本）大模型 |
| GLM-5.3-Flash | 智谱 AI 的轻量化纯文本对话模型 |
| BMI | Body Mass Index，身体质量指数 |
| BMR | Basal Metabolic Rate，基础代谢率 |
| TDEE | Total Daily Energy Expenditure，每日总能量消耗 |

### 3.5 状态判定模型

`nutrition.js` 中的 `evaluateNutrient()` 函数统一判定 8 项营养素的状态：

| 营养素 | 类型 | 达标区间 | 偏少阈值 | 轻微超标 | 严重超标 |
|---|---|---|---|---|---|
| 热量 / 碳水 | range | 0.8x – 1.0x | < 0.8x | 1.0x – 1.2x | > 1.2x |
| 蛋白质 / 膳食纤维 / 饮水 | min | ≥ 0.8x | < 0.8x | — | — |
| 脂肪 / 糖分 / 钠 | max | ≤ 1.0x | — | 1.0x – 1.2x | > 1.2x |

四级预警色彩：达标（薄荷绿 `#3d8a70`）/ 偏少（浅鹅黄 `#a98a26`）/ 轻微超标（暖橙 `#b0652b`）/ 严重超标（珊瑚红 `#bd5252`）。

## 四、AI 技术方案

### 4.1 AI 技术选型理由

| 技术决策 | 选型 | 理由 |
|---|---|---|
| 视觉模型 | 智谱 GLM-4V-Flash | 轻量视觉模型，响应快（< 3s），适合食物识别场景；OpenAI 兼容端点，便于切换 |
| 对话模型 | 智谱 GLM-5.3-Flash | 纯文本模型，比视觉模型更经济；支持 tool calling；Flash 版延迟低，适合流式体验 |
| RAG 框架 | 自研（2 字滑窗 + 加权打分） | 避免引入 LangChain.js 等重依赖；前端本地检索毫秒级响应；可解释（召回条目直接展示） |
| Agent 框架 | 自研 Plan-and-Execute + function calling | 复杂任务结构化规划、白名单执行、结果校验与一次受控重规划；简单任务保留反应式工具调用 |
| 流式协议 | SSE（`text/event-stream`） | 比 WebSocket 更简单，服务器单向下行足够打字机效果；原生 EventSource / fetch + getReader() 都支持 |
| 降级架构 | 三层（云端 → Mock → 本地知识库） | 保证任何网络环境下功能不中断，答辩演示更稳妥 |
| API Key 管理 | Node 代理持有 | 前端直连会导致密钥泄露（打包进 JS 后任何访客可看）；代理模式 + 仅监听 localhost 保证安全 |

### 4.2 AI 集成方式

#### 4.2.1 食物识别链路

```
前端 uploadDataURL
    │ visionAdapter 标准化参数
    ▼
POST /api/recognize { image, hint, clues }
    │ Node 代理：validate.js 校验 → modelClient.callVisionModel()
    ▼
智谱 GLM-4V-Flash { model, messages: [{ role: 'user', content: [image_url, text_prompt] }] }
    │ 响应：JSON { food_name, weight_estimate, confidence, nutrition_per_100g, tags }
    ▼
前端 FOOD_DB 匹配（food_name → 标准条目）
    │ 失败则直接用模型返回的 nutrition_per_100g × (weight/100)
    ▼
渲染识别结果卡片 → 用户确认后 dietStore.addRecord()
```

#### 4.2.2 对话助手链路（含 Plan-and-Execute Agent）

```
用户输入
    │ aiChat.ts 编排层
    ├── ① 个性化上下文：userStore + dietStore → system prompt
    ├── ② RAG 检索：本地知识库 tokenize + 加权打分 → Top-4 注入
    ├── ③ 复杂任务判定
    │      ├── 复杂：生成 2–5 步计划 → 白名单校验 → 逐步执行 → 校验 / 重规划
    │      └── 简单：直接进入反应式 Function Calling
    │
    ▼
POST /api/chat { messages, tools }
    │ Node 代理：modelClient.streamChatModel() → SSE 推送
    ▼
智谱 GLM-5.3-Flash（支持 tool_calls）
    │
    ▼
前端 SSE getReader() 增量解析：
    ├── delta.content → 打字机效果
    ├── delta.tool_calls → 累加 tool_call 队列
    └── 消息完成 → 判断是否有未执行的 tool_calls
         │
         ├── 有：executeTool()（7 个工具）→ 把 tool 消息追加到 messages → 再次请求（最多 4 轮）
         └── 无：完成
```

#### 4.2.4 反事实营养干预模拟

项目不仅回答“应该少吃什么”，还会基于当前真实记录计算“如果这样调整，会发生什么”：

1. 从今日记录识别主要糖来源和蛋白质、纤维缺口；
2. 生成控糖、补蛋白、均衡优化等最小调整方案；
3. 使用与营养报告相同的本地算法重新计算热量、糖、蛋白质、纤维和健康评分；
4. 横向展示调整前后数值，模型解释每个方案的收益与代价；
5. 用户点击“采用此方案”后才修改真实记录，模型和模拟工具均无直接写入权限。

例如只把奶茶减半虽然降低糖分，但可能进一步扩大热量缺口、导致综合评分下降；系统会据此说明为什么“控糖 + 补蛋白 + 补纤维”比单纯少吃更合理。这是基于确定性规则的反事实比较，不宣称医疗效果预测。

#### 4.2.5 Agent 规划与安全边界

- 规划结果采用结构化 JSON，包含目标、摘要、步骤、工具和参数，不展示隐藏思维过程；
- 仅接受 6 个白名单工具，参数在前端再次裁剪和规范化；
- 每个计划限制 2–5 步，工具失败最多触发一次受控重规划；
- 历史记录不足时改用今日真实数据，并要求最终回答明确数据局限；
- 写入型工具仍只生成待确认卡片，规划器不能绕过用户二次确认；
- 页面实时展示步骤状态和结果摘要，完成后可折叠查看完整执行证据。

### 4.3 优化策略

#### 4.3.1 性能优化

| 优化点 | 方案 | 效果 |
|---|---|---|
| 首屏加载 | 路由级懒加载 + ECharts 按需引入 | 首屏 JS 仅 ~144KB（gzip 49KB） |
| RAG 检索 | 索引懒构建 + 纯前端打分排序 | 毫秒级响应，完全离线可用 |
| 流式对话 | SSE + getReader() + 空闲超时重置 | 打字机效果流畅，长回答不被截断 |
| 图片请求体 | 服务端 8MB 上限 + 前端 dataURL 压缩 | 避免超大图片拖慢识别 |

#### 4.3.2 成本优化

- 视觉模型仅用于识别，对话用更经济的 Flash 版文本模型
- RAG 在前端执行，只把 Top-N 召回结果注入 prompt，控制 token 消耗
- Agent 最多 4 轮工具调用，防止无限循环消耗额度

#### 4.3.3 稳定性优化

| 场景 | 处理 |
|---|---|
| 云端超时（> 20s） | 自动降级 Mock → 本地知识库 |
| 429 限流 | 不重试，直接降级 |
| 5xx 服务端错误 | 指数退避重试 2 次后降级 |
| API Key 未配置 | 启动即切换 Mock 模式，不报错 |
| 断网 | 自动切换本地知识库规则引擎 |

#### 4.3.4 安全优化

| 措施 | 说明 |
|---|---|
| API Key 仅存 Node 进程 | `.env` 文件由 `server/env.js` 读取，从不打包进前端产物 |
| 写操作二次确认 | Agent 的 `add_diet_record` 必须用户点击确认才落库，防止模型误操作 |
| 入参校验 | `validate.js` 对图片格式、体积、文本长度做严格校验，防止恶意请求 |
| 无数据库 | 纯前端 localStorage，不涉及 SQL 注入风险 |

## 五、核心功能实现

### 5.1 首页总览（简洁 / 专业双模式）

**默认简洁模式**：只展示今日热量进度条、饮水进度条 + 一条优先提醒文案。文案规则（`nutrition.js` 的 `buildDailyBrief()`）：
1. 先正向夸奖（热量达标 > 蛋白达标 > 饮水达标 > 无超标 > 兜底「继续加油」）
2. 再只输出 1 条优先级最高的超标建议，用人话表达（如「🍬糖分偏高，大概率来自奶茶甜品，建议减少甜饮」）
3. 禁止堆砌多条、禁止直接展示超标百分比

**专业模式**：点击「查看详细营养」切换，展开 8 项 StatTile 指标卡 + 完整进度总览表（每项显示 emoji + 名称 + 实际值/目标值 + 进度条 + 状态标签）。

AI 营养评语模块上移至简洁进度区下方、详细营养模块上方，让用户打开页面优先看到饮食结构的总结分析。

### 5.2 AI 食物识别

核心数据结构（`aiRecognition.js`）：

```js
{
  food: { id, name, emoji, nutrition: { calories, protein, fat, carb, fiber, sugar, sodium } },
  grams: Number,               // AI 估算分量
  source: 'cloud' | 'mock' | 'local',  // 结果来源标识
  confidence: Number,          // 识别置信度
  healthTags: Array<String>   // 健康标签（高脂/高糖/优质蛋白…）
}
```

识别历史用 `sessionStorage` 持久化（同标签页内切换路由不丢失），数据超过 1.2MB 时不保存预览图，优先保住识别结果。

### 5.3 AI 营养对话助手

**个性化上下文注入**（`aiChat.ts` 的 `buildContextText()`）：

```
你正在与一位注册营养师对话。以下是关于我的信息：
【身体数据】BMI 22.3（标准）| BMR 1450 kcal | TDEE 1895 kcal | 每日推荐摄入 1895 kcal
【今日饮食】已记录 3 餐，健康评分 76（良好）
【今日营养合计】热量 1832/1895 kcal | 蛋白 79.9/109 g | 脂肪 59/67 g | 碳水 259.5/344 g | 纤维 10.4/25 g | 糖 107.4/25 g（超标） | 钠 2390/2000 mg（略高） | 饮水 220/2400 ml
```

**RAG 检索算法**（`aiChat.ts` 的 `tokenize()` + 打分）：
1. 中文 2 字滑窗 + 英文按词切分得到 query tokens
2. 对 916 条知识条目计算 token overlap 得分
3. 科普文章权重 ×3，食物相克 ×2，健康习惯 ×1
4. 召回 Top-4 注入 prompt，并在 UI 中展示给用户核对

**Agent 工具调用**（`aiTools.ts`）：
- 定义 6 个 function（JSON Schema 格式），每次对话请求随 messages 一起发送给模型
- 前端循环：解析 SSE 中的 `tool_calls` → 执行对应函数 → 把 tool 消息追加到 messages → 再次请求模型
- 最多 4 轮，每轮在 UI 中展示调用轨迹
- `add_diet_record` 工具触发后弹出待确认卡片，用户点击「确认添加」才执行落库

**SSE 流式解析**（`aiClient.ts`）：
```js
const response = await fetch('/api/chat', { method: 'POST', body: JSON.stringify(payload) })
const reader = response.body.getReader()
const decoder = new TextDecoder()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  // 解析 SSE data: 行 → JSON → 累加 delta.content / delta.tool_calls
}
```

### 5.4 健康评分模型

可解释加权算法（`nutrition.js` 的 `buildReport()`）：

| 营养素 | 权重 | 评分规则 |
|---|---|---|
| 热量 | 25 | 达标区间（0.8–1.0x）得满分，偏离按比例扣分 |
| 蛋白质 | 15 | 实际 ≥ 0.8x 目标得满分，每低 10% 扣 10 分 |
| 膳食纤维 | 20 | 每 1g 缺口扣 4 分，满分 25g |
| 脂肪 | 10 | 超目标每 10% 扣 5 分 |
| 碳水 | 10 | 超目标每 10% 扣 3 分 |
| 糖分 | 10 | 超目标每 10% 扣 4 分 |
| 钠 | 10 | 超目标每 100mg 扣 2 分 |

总分 → 0–100 分，映射为优秀（≥ 85）/ 良好（70–84）/ 及格（60–69）/ 需改善（< 60）四个等级。

### 5.5 路由守卫

```js
router.beforeEach(() => {
  if (!isLoggedIn()) redirectToLogin()  // 未登录 → 跳转独立 login.html
  return true
})
```
登录态存储：勾选「记住我」→ localStorage；未勾选 → sessionStorage。与业务数据键（`ai_nutrition_profile_v1` / `ai_nutrition_diet_v1`）完全隔离，退出登录不影响健康档案与饮食记录。

## 八、创新点

### 8.1 技术创新点

| # | 创新点 | 说明 | 对比现状 |
|---|---|---|---|
| 1 | **可解释的 RAG 检索** | 自研 tokenize（中文 2/3 字滑窗 + 英文按词切）+ 加权打分（科普 ×3 / 相克 ×2 / 习惯 ×1），召回条目直接展示给用户核对 | 市面上多数 RAG 问答只返回答案，不公开检索依据 |
| 2 | **自研规划执行型 Agent** | 复杂目标先生成结构化计划，再执行真实数据工具、校验结果并进行一次受控重规划；简单问题走低延迟 Function Calling，无 LangChain 等重依赖 | 同时满足规划、工具调用和自主决策，并控制前端项目体积与调用成本 |
| 3 | **三层降级架构** | 云端大模型 → 服务端 Mock → 本地知识库 + 规则引擎，任何网络环境下功能不中断 | 多数 AI 功能强依赖网络，答辩现场断网即失效 |
| 4 | **营养算法前后端同源复用** | `nutrition.js` 的 BMI/BMR/TDEE/状态判定/评分模型纯前端实现，无需后端服务即可计算，也便于单元测试 | 传统营养应用把算法放在服务端，增加部署复杂度 |
| 5 | **密钥与业务物理隔离** | API Key 仅在 Node 代理进程的 `process.env` 中读取，前端零密钥；写操作（Agent add_diet_record）必须用户二次确认才落库 | 前端直连大模型会导致密钥泄露，任何访客打开 DevTools 即可窃取 |

### 8.2 应用创新点

| # | 创新点 | 说明 | 对比现状 |
|---|---|---|---|
| 1 | **「先夸奖、再建议」的文案规则** | `buildDailyBrief()` 先给正向反馈（热量/蛋白/饮水达标 → 依次夸奖），再只输出 1 条最高优先级超标建议，用人话表达（如「🍬糖分偏高，大概率来自奶茶甜品」） | 市面上多数健康应用超标提示「超标 XX%」堆砌多条，造成焦虑感 |
| 2 | **简洁 / 专业双视图首页** | 默认简洁模式（热量进度 + 饮水进度 + 一条提醒），点击切换到专业模式（8 项指标 + 完整进度总览），既满足小白用户又满足专业用户 | 多数产品要么信息过载要么过于简单，缺少渐进式展示 |
| 3 | **AI Agent 写入工具的二次确认机制** | Agent 的 `add_diet_record` 工具触发后弹出待确认卡片，用户点击「确认添加」才落库，防止模型误操作 | 多数 Agent 产品调用写入工具直接执行，存在安全隐患 |
| 4 | **健康评分的可解释加权模型** | 0–100 分，7 项营养素各有权重（热量 25 / 蛋白 15 / 膳食纤维 20 / 脂肪 10 / 碳水 10 / 糖 10 / 钠 10），评分公式完全透明可复核 | 多数 AI 健康评分不公开计算逻辑，用户无法理解为什么得这个分 |
| 5 | **轮换温柔营养短句** | 首页空白区域 6 秒轮换展示（如「🌿 慢慢吃，七分饱」「💧 每隔 1.5 小时喝 200ml 水」），不遮挡功能按钮，营造治愈氛围 | 多数产品首页信息密度高、压迫感强，缺少情感化设计 |
