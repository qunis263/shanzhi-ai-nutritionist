## 一、开场与项目定位（0:00–0:20）

**画面 / 操作提示**

停在登录页，鼠标缓慢移向登录框；登录后进入首页，画面稳定在项目标题与今日概览上。

**口播文字**

> 大家好，我是参赛选手×××。这是我们做的「膳知·AI 营养分析师」——一个把拍照识别、饮食记录和 AI 营养咨询打通的营养管理工具，让记录一顿饭从几分钟缩短到几秒钟。

**字幕要点**

- 项目名称：膳知 · AI 营养分析师
- 一句话定位：拍照识别 + 饮食记录 + AI 营养咨询

## 二、用户痛点与解决方案（0:20–1:10）

**画面 / 操作提示**

切到首页，依次指向热量进度、饮水进度与主线入口；讲到技术栈时可短暂切到项目 README 的架构图。

**口播文字**

> 先说我们看到的两个痛点。第一，记饮食太麻烦：要查热量、称重量、选餐段，大多数人坚持不过三天。第二，很多 App 只告诉你吃了多少，却不告诉你下一顿该怎么改，更说不出为什么。
>
> 膳知的思路是三步：用图像识别降低记录门槛，用可解释的评分算法做营养评估，再用大模型把建议讲成人话。前端是 Vue 3 加 Vite，AI 能力通过一个零依赖的 Node 代理接入云端模型，密钥只留在服务端。

**字幕要点**

- 痛点：记录成本高、建议不具体
- 方案：识别降门槛 → 算法做评估 → 大模型讲人话
- 技术栈：Vue 3 + Vite + 轻量 Node 代理

## 三、首页主线与饮食记录（1:10–1:50）

**画面 / 操作提示**

首页指向「识别 → 记录 → 报告 → 微干预」四步卡片；点击进入饮食记录，搜索「鸡蛋」，选水煮蛋，输入 80 克，加入早餐。

**口播文字**

> 登录后是首页。这里把今天最该做的事压缩成一条主线和四个入口：识别、记录、报告、微干预，点一下就能到。
>
> 我们先用最普通的方式记一餐。进入饮食记录，搜索鸡蛋，选水煮蛋，输入八十克，加入早餐。全天的热量和七大营养素会立刻累加，并与目标值对比。食物库内置九百一十五种常见食物，支持模糊搜索和份量换算。

**字幕要点**

- 首页四步：识别 → 记录 → 报告 → 微干预
- 915 条食物库，支持搜索与份量换算
- 记录后全天营养实时累加

## 四、拍照识别餐食（1:50–2:45）

**画面 / 操作提示**

进入「AI 食物识别」，上传一张餐食照片，展示压缩后的预览；等待识别结果，依次指出来源徽标、判定依据、候选排名；最后点「咨询 AI」。

**口播文字**

> 但更多时候，用户不知道食物叫什么，也懒得称重。这时直接拍照。
>
> 这张照片在上传前会先在浏览器里压缩到最长边一千二百八十像素，减少请求体积和等待时间。后端调用智谱 GLM-4V 视觉模型，返回食物名称、置信度和候选排名。
>
> 这里有一个刻意的工程约束：模型给出的食物名，必须能在本地食物库里绑定到具体条目，才允许输出营养值；绑定不上就明确提示，并且禁止写入记录。我们宁可少识别一个，也不让模型编造热量。
>
> 识别完可以一键带着食物、分量和营养数据去咨询 AI，而不是只丢给模型一张图片。

**字幕要点**

- 上传前浏览器压缩：最长边 1280px
- GLM-4V 识别 + 本地食物库绑定
- 绑定失败禁止写入，杜绝编造营养值
- 识别结果可携带结构化数据继续咨询

## 五、营养分析报告（2:45–3:25）

**画面 / 操作提示**

进入「AI 营养分析报告」，展示健康总分仪表盘与 AI 评语；向下滚动到评分构成明细、超标项与缺口项；最后点一下「导出 PDF / 打印」。

**口播文字**

> 记录和识别都会进入同一份报告。报告不是让大模型随口点评，而是先用本地加权模型算出零到一百分的健康总分，再让模型基于这些确定性数据生成评语。
>
> 页面会拆开告诉你：每一项指标权重多少、实得多少、超标在哪、缺口在哪。报告支持直接导出 PDF，方便留存或给医生看。

**字幕要点**

- 0–100 分本地加权评分，模型只负责评语
- 评分构成、超标项、缺口项全部可追溯
- 支持导出 PDF / 打印

## 六、7 天微干预（3:25–4:10）

**画面 / 操作提示**

进入「7 天微干预实验」，展示三种模拟方案的评分对比与推荐理由；点击创建实验，展示每日打卡与效果曲线。

**口播文字**

> 知道问题还不够，关键是下一步怎么改。我们做了七天微干预：系统基于今天的真实饮食，模拟控糖、补蛋白、均衡优化三种方案，比较调整前后的评分差异，并解释为什么这一种更适合你。
>
> 用户确认后才会写入计划，之后每天打卡，系统用真实记录校准效果。这样营养建议就从一句空话，变成了可执行、可验证的一周实验。

**字幕要点**

- 三种方案模拟：控糖 / 补蛋白 / 均衡优化
- 对比调整前后评分，说明推荐理由
- 用户确认后写入，每日打卡、真实数据校准

## 八、AI 营养对话与 Agent（4:40–5:30）

**画面 / 操作提示**

进入「AI 营养对话助手」，输入「我今天晚饭吃什么」；展示个性化上下文与流式回答；再输入一个复杂任务，展示计划步骤与工具执行轨迹；最后点一下语音输入或播报按钮。

**口播文字**

> 接下来是 AI 营养对话。它知道你今天的 BMI、基础代谢、饮食模式和已经吃进去的营养，所以问「晚饭吃什么」，回答不是泛泛而谈。
>
> 复杂问题会进入 Agent 模式：先生成两到五步计划，再调用真实的数据工具查询、计算、模拟，最多四轮，过程实时可见；涉及写入的操作必须用户确认。
>
> 回答走 SSE 流式输出，浏览器支持时还可以语音输入和播报；不支持时自动保留文字交互，不影响使用。

**字幕要点**

- 个性化上下文：BMI / 基础代谢 / 今日摄入
- Agent：2–5 步计划、真实工具、写入需确认
- SSE 流式输出；语音不可用时降级为文字

## 九、AI 技术亮点与工程取舍（5:30–6:25）

**画面 / 操作提示**

切到 README 的三层降级架构图，再切到「AI 能力评测」页面，展示五维指标、消融实验和失败案例。

**口播文字**

> 最后讲三个技术取舍。
>
> 第一，为什么用代理：密钥一旦进浏览器就等于公开，所以我们用零依赖的 Node 服务持有密钥并转发，前端只认一个接口。
>
> 第二，稳定性：云端超时、限流或者没配密钥时，系统按云模型、Mock、本地可解释引擎三级降级，并明确标注来源。演示不会因为网络中断而翻车，但真实云端识别和对话仍然需要网络、密钥，也有调用频率限制。
>
> 第三，不吹准确率：我们用五十条固定用例做离线评测，拆开看事实覆盖、个性化、检索命中和安全边界，报告里保留失败案例。检索用 BM25 加本地语义向量双路召回，再做融合排序。这些分数衡量的是工程链路，不是模型准确率。

**字幕要点**

- 密钥只在 Node 代理，不进浏览器
- 三级降级：云端 → Mock → 本地可解释引擎
- 50 条固定用例离线评测，保留失败案例
- BM25 + 本地语义向量双路召回
